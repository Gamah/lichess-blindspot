| 55 | **Deliberate re-fetch of one game, by id — and the per-position delete it unlocks.** Now that the pipeline has a forward cursor and a "how far back" dial, the one thing still unreachable is a *specific* game that has been dropped: `meta.analysed`/`meta.fetched` still name it, so the paging skips it forever, and `purgeGames`/`forgetGame` leave those lists untouched. Delete was built and removed (see CLAUDE.md) for exactly this — deleting a game lost the analysis *and* the game. `/game/export/{id}` has **no concurrency limiter at all** (unlike the by-user export), so one game can be pulled back on demand without touching the one-per-IP budget the batches live under; `fetchGames` would need a sibling that takes an id, and whatever deletes must drop the id from both lists or the game is fetched and then ignored forever. With that, deleting a game costs only the engine time, which is a trade someone can reasonably choose, and per-position delete becomes honest. |
| 50 | **`GET /api/cloud-eval` as a source of `alts`, measured before it is built.** Verified live 2026-08-15 03:20 UTC (one request, `-o` to a file): `200`, `access-control-allow-origin: *`, `multiPv=5` returns five pvs best-first. `controllers.Api.cloudEval` is `AnonOrScoped()` — no token — rate-limited `3_000/day` per IP at cost 2 anonymous, so ~1500 lookups a day, and a miss is a cheap 404. `cp` is already White's POV: `ui/lib/src/ceval/protocol.ts:118` inverts on ply, `evalCache.ts` `toPutData` sends unmodified, `JsonView.writePv` re-emits untouched. The store is fed by analysis boards at `depth >= 20` or `nodes > 3e6`, which is the budget `rank-stability.ts` measured at ~26 s a position and this project rejected as unaffordable — so a hit is a *better* ranking than we can compute and, more to the point, **the same ranking on every device**, which is the flaw `altsMs` exists to admit. **Hit rate decides whether this is worth any code, and the honest prior is that it is low**: evalCache holds positions someone opened on a board, ours are blunders 20–40 plies into ordinary ~1100 games. So step one is `scripts/cloud-hit-rate.ts` over `.cache/corpus.pgn` via `parsePgn`/`relaxedCandidates` — sample ~300 candidates (600 of the daily budget), cache replies under `.cache/cloud/`, report hit rate, **`pvs.length >= 5` rate** (the one that matters), depth spread, and whether cloud `pvs[0]` agrees with our stored `alts[0]`. Put the table in CLAUDE.md whichever way it comes out; a measured "the cache does not know our positions" closes the question permanently. Only past roughly 15% usable is the rest worth writing: a `cloudRank(fen)` in front of `rankPosition` (`src/engine/analyse.ts:179`, the single choke point), passed in through `rankCandidates`' opts so the node harness can fake it. Two traps. `makeBestMultiPvEval` **falls back to fewer pvs rather than failing**, so a 2-pv reply taken as `alts` silently turns Medium's top-5 gate into a top-2 gate — reject anything under `RANK_LINES`. And `altsMs` cannot describe a depth-limited ranking, so it needs an optional `altsDepth` sibling that `unrankedPlies` treats as satisfying any `rankMs` (never re-rank a depth-40 cloud line with a 4-second local one) and that `derivedKey` stamps, or the deck will not rebuild when one lands. Not a schema bump. **This does not make "no engine" a supported mode** — coverage is partial and unknowable per position, and Easy still searches for a move outside the ranking. |
