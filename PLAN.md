| 75 | A game skipped because the engine could not start is recorded in `meta.fetched` — "looked at, found nothing" — and so is never analysed again, even once there is an engine. A session with no engine therefore walks backwards through someone's whole history stamping it, silently, and the deck never fills. Seen for real on a phone: 70 games. The isolation fix makes the engine-less load rarer but not impossible — a dropped 15 MB net download does it too, and `App.engine()` caches that failure for the session. Fix: a separate `meta.needsEngine` list, re-queued from IndexedDB when an engine appears, and stop paging further back while that backlog grows. `Pipeline.rankBacklog` is now the shape to copy — it already walks the stored games once per session looking for work the engine owes them — but it does not cover this case, because a game stamped into `meta.fetched` has no analysis at all and so yields no candidates to rank. |
| 70 | The loading screen rewrites its whole DOM on every progress event, which is once per swept position. Fine until it isn't; measure before caring. |
| 60 | Confirm the blocked-storage fix with the Firefox user who hit `SessionStorage - Security error: The operation is insecure`. Three defects were found and fixed by reading (module-scope `createStore` in `assetCache.ts` killing the whole bundle at import, unguarded `sessionStorage` in `isolation.ts` with no catch in `main.ts`, eager store in the `Profile` constructor), but none was reproduced — there is no Firefox on the dev host. Worth asking: did the page render at all or was it blank, what was the console stack, and are cookies blocked for the site / is it a private window. Expect a **broken** app, not a degraded one: browsers that block storage usually block service workers too, so no isolation and no engine, and since positions are now withheld until the engine has ranked them there is no deck at all. That is deliberate (see CLAUDE.md) and `engineNag` says so with a report link — so what to ask for is the nag's diagnostics line, which is the whole bug report. |
| 55 | `App.buildDeck` replays every stored game through chessops on the main thread, at every load and on every Settings click that rebuilds. Measured on the dev host: ~450 ms for 200 games of 120 ply, 96% of it in `replay` — `parseSan` is a full move generator and `makeFen` runs twice a ply, ~18 µs/ply. A mid-range phone is 3–5× slower, so 0.8–1.4 s of blocked thread on a big history, with no spinner behind the Settings clicks. Games with no `analysis` cost nothing (`puzzlesFromGame` returns before `prepareGame`), so this only bites someone with a lot of *analysed* history. Cheapest real fix is to cache the derived deck per game in memory and rebuild only what changed; a worker is the bigger hammer. |
| 50 | `RANK_MOVETIME` was set from 10 positions in a single game (see the table in CLAUDE.md), which is enough to show that more search time does not buy a more stable top 5 but not enough to set a number confidently. Re-run `scripts/rank-stability.ts` over several games — it takes a game id, so a handful of saved exports in `test/` would make it repeatable — and in particular measure how often Hard's top-2 boundary refuses a move a deep search ranks second, since that is the setting the number actually decides. The corpus half of this now exists: `scripts/pgn.ts` reads a browser-downloaded PGN dump of one player's history (which is what the by-user export gives a browser, and the only way to get a real corpus onto the dev host), and `scripts/decided-band.ts` shows the shape to copy — take the dump, take the player's name, walk every candidate. |
| 45 | Opening-book cancellation is gone: `explorer.lichess.ovh` answers 401 to a browser on an ordinary connection as well as to this host, and lila's own frontend calls it with `credentials: 'include'` — a lichess session cookie a static page on another origin cannot have. The opening is cut off by `division.middle` again, which is what the failing lookups amounted to anyway. Bring it back only if a way to call it without a lichess session appears; the code is in git, one commit before this row was written. |
| 40 | `App.buildDeck` swaps `this.deck` out while a puzzle is on screen, so the served puzzle is back in `pending` of the new deck with `served` unset. `Deck.requeue` ignores an id already pending, which stops Skip duplicating it, but the position can still come round again immediately after a Skip, and Bring-back-solved re-records the finished on-screen puzzle as solved. Wants `Deck` to be told what is currently served, or `buildDeck` to re-serve it. |
| 35 | The eval test is loosest exactly where the move played was worst — measured, `after` below -0.8 accepts 57% of all legal moves against 23% near equality (see the table in CLAUDE.md). `IMPROVE_DIFF` is a flat 0.04 against `puzzle.eval`, so a catastrophic blunder sets a low bar and Easy accepts nearly anything that is not also catastrophic. Worth scaling the margin by the headroom the position actually has, so that beating a -9 blunder by a hair is not a win. Small: it is one expression in `judgeEval` and it touches nothing stored, so it is retroactive and free to tune. Do **not** solve this by withholding positions — that was row 65, and it would delete the most instructive puzzles in the deck. Only 3% of candidates are free wins at all, so measure whether this is worth doing before doing it.
